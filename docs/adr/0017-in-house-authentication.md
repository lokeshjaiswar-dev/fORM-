# ADR-0017: In-house authentication on our own tables

- **Status:** Accepted (delivery plan decision D4: decided)
- **Date:** 2026-10-19 (written up; the decision was taken in the v1.1 planning set, architecture §10)
- **Work package:** WP-1.01 (feature matrix rows WSP-01, WSP-08; CMP-21 for builder-user data)

## Context

The auth library was an open decision (D4). The platform must run air-gapped, send no telemetry, keep identity data in its own Postgres under RLS and the audit log, and leave a clean seam for enterprise SSO through BoxyHQ Jackson in P3. A third-party auth framework brings its own tables, sessions and network expectations. See [`docs/platform/03-architecture.md` §3.3](../platform/03-architecture.md).

## Decision

1. **Authentication is built in-house** on the architecture's identity tables, with no third-party auth framework.
2. Building blocks: argon2id passwords (`@node-rs/argon2`), magic links, Google and Microsoft OIDC through `openid-client` (SaaS only), server-side sessions in the `__Host-fr_sess` cookie with rotation on privilege change, password reset, TOTP 2FA with 10 hashed recovery codes, and per-IP and per-account throttling.
3. CSRF is the Fetch-Metadata and header guard of [ADR-0008](0008-csrf-fetch-metadata.md).
4. Every auth event is audited, failures and denials included.
5. SSO, SCIM and LDAP arrive in P3 through Jackson, behind the same session model.

## Consequences

- Works offline and air-gapped; OIDC is hidden when egress is off. Without SMTP, admins issue one-time codes for invites, resets and DSR identity checks.
- The team owns the security of the auth code: WP-1.01 includes a session-fixation test and CODEOWNERS cover `authz/`.
- Login and session lookups before a tenant is known go through the definer functions `auth_user_by_email` and `auth_session` ([ADR-0015](0015-rls-tenancy-and-definer-functions.md)).

## As built (WP-1.01)

- **Tables** (migration `0006_auth.sql`, `packages/db/src/schema/auth.ts`): `sessions`, `user_identities`, `auth_tokens` (email verification 24 h, magic link 15 min, password reset 1 h, MFA ticket 5 min with 5 attempts; SHA-256 of the token only) and the UNLOGGED `auth_throttle`. Identity rows are the user's, not an org's: their policies are `user_id = app_user()` for a user actor, and the requests run in `withUser()` (no org; audit records go to the platform chain). Isolation suites run for every actor kind; fr_app cannot read `token_hash`, `ip_hash`, password hashes or TOTP secrets, and has no privilege at all on `auth_throttle`. The credential columns of `users` (password hash, TOTP secret, step and enablement, recovery codes, verification time) can change only in `withUser()` or a definer function: a trigger refuses them in an org-scoped transaction. Revocation and redemption are final for every role: triggers refuse changing a session's `revoked_at` or `revoked_reason` once set, or a token's `consumed_at`, so no bug can bring back a signed-out session or a used link.
- **Definer functions** beyond the two named above: `auth_user_credentials(user_id)` (the second factor and credential changes), `auth_create_user()` (sign-up and first OAuth sign-in), `auth_recovery_code_use()`, `auth_identity_user()`, `auth_token_take()` (single-use redemption), `auth_token_peek()` (the account a live verification or sign-in link is for, without using it), `auth_mfa_ticket()` (counts attempts) and `auth_throttle_hit()`. `auth_session(token_hash, idle_seconds)` returns the session in any state (active, revoked, expired, user inactive) so a rejected cookie is audited with its reason, and slides the idle expiry (12 h, never past the 14-day absolute expiry) at most once a minute.
- **Sessions**: `mfa_level` is the first factor (`pwd`, `link`, `oauth`; `sso` in P3) plus the second when one was used (`+totp`, `+recovery`). Every sign-in issues a fresh token and revokes the session the same browser presented for the same user (session fixation); turning TOTP on or off rotates the session, and turning it on signs out every other session; a password reset revokes them all. Setting up an authenticator needs a sign-in from the last 15 minutes (`REAUTH_REQUIRED` otherwise), so a session taken over later cannot enrol the attacker's authenticator and lock the owner out.
- **TOTP**: RFC 6238 (SHA-1, 6 digits, 30 s, one step of drift), a code is never accepted at or before the last accepted step. The secret is sealed with AES-256-GCM under a per-secret data key bound to the user id; the data key is wrapped by the KMS port (`KMS_KEYFILE_PATH`, required in production). Ten recovery codes of 80 bits, stored as SHA-256.
- **Passwords**: argon2id (m = 64 MiB, t = 3, p = 1), 8 to 128 characters, the NCSC top 100,000 list (entries of 8 characters or more, `apps/api/scripts/denylist.ts`), not the address; HIBP k-anonymity when `PASSWORD_BREACH_CHECK=hibp` (default on SaaS with open egress, never when air-gapped). An unknown address costs one argon2 verification like a wrong password, and answers the same.
- **Email links** carry the token in the URL fragment of a builder page, so it never reaches a server log or a Referer. Mail goes through the Mailer port in the background once the transaction that issued the link has committed (WP-0.15 SMTP adapter to Mailpit in development; `MAILER_DRIVER=log` logs subject and recipient count only). A magic-link or OAuth sign-in that verifies a never-verified account drops that account's password, since someone else may have opened it with the address. The verification link is bound to the browser that signed up (`__Host-fr_signup`, an HttpOnly cookie with a keyed hash of the link's token, set at sign-up whether or not the address was free): in any other browser a never-verified account with a password also needs that password (`PASSWORD_REQUIRED`, checked before the link is used), so the owner of an address someone else registered never verifies it for them, and takes it over with a reset instead. The builder's link pages first look the link up (`POST /v1/auth/link`), show the address and redeem the link only on a "Continue as …" click, so a link someone else sends cannot silently sign a browser into their account.
- **OAuth**: `openid-client` with PKCE (S256), state and nonce kept in a signed, 10-minute `__Host-fr_oauth` cookie. Routes exist only for providers configured with `OIDC_<PROVIDER>_*`, and only on SaaS: on-prem the settings are ignored with a start-up notice, so air-gapped installs have no OAuth routes and `GET /v1/auth/methods` offers none (the builder also hides the buttons in an air-gapped edition). An account is found by its linked identity, else linked to the user with the same verified address (Google `email_verified`; Microsoft Entra ID `xms_edov`, which the app registration must emit as an optional claim, or `email_verified`), else created. A user with TOTP still needs it after OAuth. Tested against the mock provider in `@form/testkit` (`startMockOidcProvider`).
- **Throttling** (architecture §3.5): `auth_any` (IP hash, 60 / min) on every auth request, and `auth_login` (IP hash and account, 10 / 15 min) on credential attempts and link requests; over either: `429` with `Retry-After`. Beyond §3.5: `auth_account` (account across IPs, 30 / h) counts password attempts, and once it is spent a password sign-in answers `link_sent` whatever the password and mails a sign-in link only when the password was right, so a spread-out guess learns nothing and nobody can lock the owner out; `auth_mail` (per address, 10 / h) caps the links mailed to one address (sign-up, magic link, reset, step-up; `429` naming the newest link), which failed passwords never use up; `auth_mfa` (user, 30 / h) counts every second-factor check (MFA tickets and the signed-in TOTP enable, disable and recovery-code routes share it). Each limit is audited once per window (`auth.throttled`). A cookie that leads to no session counts against `auth_any` on every route, and so does every CSRF refusal (before its `request.authorize` record), so neither junk cookies nor cross-site requests can flood the audit chain. IP hashes are `HMAC(daily salt, ip)` with the salt from `AUTH_SECRET`; behind a proxy `TRUST_PROXY` names the hop count or the proxy addresses, never `true`, so a client cannot choose its IP through `X-Forwarded-For`.
- **Audit**: every outcome is an `auth.*` event of the catalogue, on the platform chain: successes in the business transaction, refusals on the separate audit pool. Two-factor requests that do not fit the account's state (`409 MFA_ALREADY_ENABLED` / `MFA_NOT_ENABLED`) are audited as denied with `already_enabled`, `not_set_up` or `not_enabled`; a sign-out with the development header is audited with no session. Requests that fail schema validation (`400 VALIDATION_FAILED`, such as a malformed address or token) are counted against `auth_any` but not audited: they reach no account and no token. A recovery code is used up in the same transaction that takes the MFA ticket, so a refused or racing request never costs a code without a sign-in.
- **Open** (backlog BL-200 to BL-207): the PoW captcha step and a growing backoff after the login limit, auth mail through `email.send` and localised templates, purging expired auth rows, admin-issued one-time codes when there is no SMTP, real Google and Microsoft app registrations, gating the builder on a session once drafts live on the server, and the session's active org.
