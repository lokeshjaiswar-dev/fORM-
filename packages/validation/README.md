# @form/validation

Answer validation (FND-05, VAL-01, VAL-05, VAL-07, VAL-10, RSP-02; `docs/platform/02-form-schema-v2.md` §3.3.8–9): the same function decides Next in the renderer and the 422 in the submission pipeline. Pure and isomorphic: no React, DOM, `FileList`, Node built-ins, clock, randomness, host locale or host regex engine.

| Path | What it holds |
|---|---|
| `src/validate.ts` | `validateAnswers(version, evalState, answers, { scope, locale, today, messages?, holidayCalendars? })` → `FieldError[]` |
| `src/normalize.ts` | I9: `normalizeAnswers` / `normalizeAnswer` turn blank control values ('', null, [], blank sub-parts) into absent keys; `isUnanswered` |
| `src/errors.ts` | Answer-schema issues → `ValidationErrorCode` (registry checks carry theirs; the twin's own issues are mapped by type), and the message arguments from the block config |
| `src/messages.ts` | Message text: block message → form system-message override → caller catalogues → en-IN source, all ICU |
| `src/checks.ts` | What the registry leaves to validation: author patterns, presets and masks, relative and field date bounds, age, holiday calendars, options hidden by logic |
| `src/pattern.ts`, `src/formats.ts` | re2js compilation (author patterns capped at 256 characters and 1000 program instructions, values at 40,000 code units), preset and mask sources |
| `src/dates.ts` | Integer calendar arithmetic on `YYYY-MM-DD` (month-end clamping, completed years) |

## Rules

- **Scope.** `{ page }` (Next) validates the input fields of that page; `'submit'` validates every page. Either way only fields that are effectively visible (`visible_eff`: the block, its ancestors and its page on the path) and enabled are validated, and only the effective required set (`required_eff` from `EvalState.required`) can report a whole-field `required` (empty path). Sub-part `required` errors (a blank typed signature name, a missing required part of a composite value) apply to any answer that is present, on optional fields too. A hidden or disabled field never blocks (B2); Next never looks past the current page (B1). Logic `submitBlocks` add `blocked_by_rule` for their page, or at Submit; in a non-default locale the message is the `rule:<ruleId>:<actionIndex>` translation (`submitBlockMessage`; the index counts `then` actions, then `else` actions), else the message as written.
- **Submit equals Next over the path.** The block errors at Submit on the complete answers are exactly the errors Next reported on each page of the path when only that page and the pages before it were answered (property test; it fails as soon as a rule reads a later block, which I8 forbids). So a respondent who passed every page cannot fail at Submit with the same answers.
- **Unanswered is absent (I9).** Answers are normalised before validation, so an empty number is `required`, never "expected number, received NaN" (B14), an empty optional choice is no error (B9), an unanswered NPS or scale is absent and 0 is a real NPS answer (B7), and a ranking is answered only once ranked; a required ranking needs every position (B8).
- **`required` first.** A missing answer reports only `required`; otherwise each `(path, code)` is reported once, in schema order. Errors follow document order, then submit blocks.
- **Hidden fields** are validated on their evaluated capture (`EvalState.values`), never on a submitted value. Computed fields (calculation, context, unique id) are produced by the server and not validated here.
- **One regex engine.** Author patterns (`SafePattern`, ≤ 256 characters), presets and masks run through `re2js` 2.8.6, a pure-JS RE2, in the browser and on the server (VAL-04, F-15), on the NFC form of the value. RE2 classes are ASCII (`\s` is not NBSP, `\w` is not Devanagari); use `\p{…}` classes for scripts. Patterns search the value (unanchored, like `RegExp#test`); anchor with `^…$`. Matching is linear in the input, but the NFA fallback costs about program size × input length and counted repetition makes a short source a large program (`(?:\pL|b){1000}` × 16 is 240 characters, 16,002 instructions, and took about 25 s on a 10,000-character value). So the cap covers program size as well as length: a pattern RE2 cannot compile (backreferences, lookaround), longer than 256 characters (`too_long`) or compiling to more than `PATTERN_MAX_PROGRAM` = 1000 instructions (`too_complex`; an RFC-style email pattern is 259, presets are under 50) is ignored at runtime and reported by `patternProblem` (B12); publish refuses it (WP-1.07). Program size alone is not enough: when the DFA runs out of states, the NFA keeps up to one thread per instruction alive and a search costs up to program size × value length steps (`(?:[\pL\pN]|b){990}$`, 993 instructions, took 11 to 25 s on a 40,000-character value in review). So an author pattern or mask is only run when program size × value length (UTF-16 code units) is at most `PATTERN_COST_BUDGET` = 250,000 (`withinBudget`); beyond it the value fails that pattern or mask. One check then stays under about 0.15 s even at the slowest rate measured (about 0.6 µs per step; about 0.03 µs on a developer machine, under 10 ms). A 1000-instruction pattern runs on values of up to 250 code units, the email pattern on 965. A value already over the field's length limit gets `too_long` alone, with no preset, pattern or mask check. Presets are fixed, anchored and under 50 instructions with one or two live threads, so they are linear with a small constant and are not held to the budget; the answer twin caps text at 50,000 code units. RE2's own limit (nested repeat counts multiply to at most 1000) keeps compiling any 256-character source under about 1 s; the result is cached. Presets check the format only (GSTIN and PAN checksums: WP-2.07).
- **Messages** (VAL-07, VAL-08): every code has an en-IN message in `@form/i18n`'s `system` catalogue. A block's `messages[code]` wins (its `block:<id>:msg:<code>` translation in other locales), then the form's `i18n.systemMessages[locale][code]`, then the caller's catalogues, then en-IN. Custom messages are ICU with the same arguments (`{min}`, `{max}`, …); one that fails to format falls through. This applies to every type, email included (B13).
- **Dates.** `today` is the date of `meta.now` in the form time zone; relative bounds and age limits are measured from it. A field bound (`{ kind: 'field' }`) reads the other block's evaluated value and is ignored while that block is unanswered or hidden.
- **Out of scope here.** Network checks (uniqueness, OTP, slot capacity, coupon, payment, file existence and scans) are appended by the API; the free-provider and disposable email lists arrive with SPM-03.

## Determinism

`test/corpus/determinism.ts` holds the regex corpus (50 patterns × 63 inputs: `\s` with NBSP and other separators, `\w` and `\b` with Devanagari, the `i` flag with ß/ẞ, Σ/σ/ς, the Kelvin sign, dotted and dotless i, Cherokee and Deseret pairs, `.` with astral, combining and lone-surrogate input, and the program-size budget), every preset, masks, and `validateAnswers` over a three-page form with logic in every scope for 200 generated answer sets. Node runs it in `test/determinism.test.ts` (digest pinned); Chromium, Firefox and WebKit run it through `pnpm test:determinism` (the CI `determinism` job, next to the logic@2 corpus) and must produce byte-identical JSON. A digest change is a change in verdicts: review it as one.

```sh
pnpm --filter @form/validation typecheck
pnpm --filter @form/validation test               # tables per type, scope property, B-bug fixes, purity, Node determinism (with coverage)
pnpm --filter @form/validation test:determinism   # the corpus in Chromium, Firefox and WebKit, diffed with Node
```
